## 1. КОНЦЕПЦИЯ СИСТЕМЫ СПЕЦИФИКАЦИЙ

1. **Единая точка истины (Master Data).** Вся номенклатура, количества, цены и сроки
   холдинга по рамочному проекту хранятся в **одном** первоисточнике — спецификации
   `work spec` (тип 20). Он живёт в каталоге рамочного договора и покрывает все заказы.
2. **Иерархия «рамка → заказы».** Рамочный договор нумеруется `N0`; каждый прикладной
   заказ — `N1, N2, N3...` и отличается значением поля `NUM PROJECT`.
3. **Производные спецификации (типы 30, 40)** генерируются автоматически из мастера
   ETL-процессором `ProcessingTable` (язык конфигураций HorizonBI). Они формируются по
   правилам отбора (раздел 5) и размещаются в каталоге конкретного заказа.
4. **Запрет ручного редактирования выходных документов.** Производные спецификации —
   результат перегенерации, а не ручного труда. Любые изменения вносятся **только
   в мастер** (`work spec`) инженером, после чего производные пересоздаются.

## 4. ПЕРВОИСТОЧНИК — СПЕЦИФИКАЦИЯ `work spec` (ТИП 20)

### 4.1. Где читаются данные
Файл (п. 3.1) — книга Excel. Основные смарт-таблицы:

| Лист | Смарт-таблица | Содержание |
|---|---|---|
| `SpecificationWork_1` | `TabSpecificationWork_1` (30 колонок) | Идентификация, номенклатура, количества, закупка |
| `SpecificationWork_2` | `TabSpecificationWork_2` (18 колонок) | Цены реализации, НДС, сроки, примечания |
| `SpecificationWork` | `TabSpecificationWork` (47 колонок) | Объединённый датасет (1:1 по ключу) — **его читают производные спецификации** |
| `TableSchema` | `TabTableSchema` (48 записей) | Метаданные колонок: типы, диапазоны, обязательность |

Связь строк Work_1 ↔ Work_2 — один ключ на позицию: **`HASH COLLECTION`**
(например `8/2026-n1-горизонт-ver_1-set_1.1-true`). Это **уникальный идентификатор
позиции заказа во всей экосистеме** — используйте его для сопоставления мастера
и производных документов.

### 4.2. Ключевые для аналитика поля (семантика)

| Поле | Смысл |
|---|---|
| `NUM PROJECT` | Шифр заказа-владельца позиции (`8/2026-N1-ГОРИЗОНТ`...) — фильтр принадлежности |
| `NUM ORDER` | Номер заказа внутри рамочного договора |
| `VER COLLECTION` | Версия позиции. В итоговые документы попадает **только старшая** версия |
| `NUM FULL SET` | Иерархический номер позиции (`1.1`, `2.3`) — сквозная нумерация комплекта |
| `DESCRIPTION SET` / `IDset` / `NUM SEQUENCE SET` | Название / идентификатор / порядковый номер комплекта оборудования |
| `NAME PRODUCT` | Наименование позиции (товара или услуги) |
| `DESCRIPTION PRODUCT` | Техническое описание и характеристики |
| `UNITS` | Единица измерения (`шт`, `компл`, ...) |
| `QUANTITY TOTAL` | Итоговое количество к поставке/выполнению |
| `DURATION SALE $TOTAL` | Срок поставки/реализации, кал. дней |
| **`isSHIPPED`** | `true` — позиция включается в производные спецификации; `false` — отсекается |
| `isSUPPLIED` | Статус обеспеченности позиции закупкой |
| **`isPROCESSING`** | `true` — по позиции запланирована **скрытая модификация** выходных значений (см. п. 5.3) |
| `COMMENT WORK` | Внутренний комментарий — **никогда не попадает клиенту** |
| `COMMENT CUSTOMER` | Примечание для заказчика — попадает в типы 30 (колонка «ПРИМЕЧАНИЕ») |
| `PRICE UNIT $TOTAL`, `COST $TOTAL`, `COST ADD VAT $TOTAL` | Клиентские цена/стоимость без НДС и сумма НДС (только для типа 40) |

Полный реестр 47 колонок с диапазонами валидации — в документации экосистемы
(`README-work_spec.md` каталога `20__work_spec` проекта разработки HorizonBI).

## 5. КАК ФОРМИРУЮТСЯ ПРОИЗВОДНЫЕ СПЕЦИФИКАЦИИ (правила чтения)

### 5.1. Отбор позиций заказа в итоговый документ (конвейер, по порядку):
1. **Фильтр заказа:** `NUM PROJECT` = шифр конкретного заказа.
2. **Отсечение незавершённых:** удаляются все строки `isSHIPPED = "false"`.
   Позиция попадает в спецификации только с флагом `true`.
3. **Детерминированный отбор версий:** из дублей позиции по `NUM FULL SET`
   остаётся строка с максимальной `VER COLLECTION`.
4. **Формирование клиентской сетки:** оставляются только разрешённые колонки
   (различаются для типов 30 и 40), затем русская локализация заголовков.

### 5.2. Состав выходных колонок — см. разделы 6 и 7.

### 5.3. Скрытая модификация (важно для объяснения расхождений)
Перед формированием документа может применяться блок адресных правок
позиций, запланированных флагом `isPROCESSING = "true"`
(разрешены только колонки с флагом `MODIFY FLAG` в `TabTableSchema`).
Следствие: **значение в производном документе может осознанно отличаться от
«сырого» значения мастера.** Не считайте такое расхождение ошибкой — оно
контролируется инженером. При выявлении расхождения фиксируйте: `HASH COLLECTION`,
колонку, значение в мастере и в производной спецификации.

## 7. СПЕЦИФИКАЦИЯ ТИПА 40 `to_customer_fin` — коммерческое предложение / финансовое приложение

**Где читается:** файл п. 3.3; лист **`SpecificationToCustomerFin`**,
смарт-таблица **`TabSpecificationToCustomerFin`**.

**Принцип:** раскрываются **только цены реализации**; закупочные цены, поставщики,
наценки, скидки — запрещены к раскрытию. Для ООО «ГОРИЗОНТ» (ОСНО 22%) применяется
**принцип чистой базы**: цены и стоимости указываются без НДС, сумма НДС — отдельной
колонкой; итог с НДС = `СТОИМОСТЬ БЕЗ НДС + НДС`.

| № | Заголовок в документе | Смысл |
|---|---|---|
| 1 | `№` | Иерархический номер позиции |
| 2 | `НАИМЕНОВАНИЕ` | Наименование |
| 3 | `ЕД ИЗМ.` | Единица измерения |
| 4 | `КОЛ-ВО` | Количество |
| 5 | `ЦЕНА БЕЗ НДС, руб` | Цена за единицу (округлённая) |
| 6 | `СТОИМОСТЬ БЕЗ НДС, руб` | Стоимость позиции |
| 7 | `НДС, руб` | Сумма НДС по позиции |
| 8 | `ДЛИТЕЛЬНОСТЬ ПОСТАВКИ, дней` / `ДЛИТЕЛЬНОСТЬ РЕАЛИЗАЦИИ, дней` | Срок |

Баланс строки обеспечен банковским округлением:
`ЦЕНА × КОЛ-ВО = СТОИМОСТЬ` — вплоть до копейки (критично для 1С заказчика).
Итоговая сумма документа = Σ`СТОИМОСТЬ БЕЗ НДС` + Σ`НДС`.

## 9. ПРАВИЛА РАБОТЫ AI-АГЕНТА

1. **Только чтение.** Никаких изменений в файлы спецификаций (ни мастер, ни
   производные) агент не вносит. Изменения исполняет инженер через мастер + перегенерацию.
2. **Определение состава позиций заказа:** читать таблицу типа 40/30 заказа (п. 6–7);
   при сверке с мастером — фильтр `NUM PROJECT`, старшая `VER COLLECTION`,
   `isSHIPPED = "true"`, ключ сопоставления — `HASH COLLECTION`.
3. **Расхождения «мастер ↔ производная»:** сначала проверить `isPROCESSING` (п. 5.3),
   затем — версию позиции; только после этого эскалировать инженеру.
4. **Ссылки на позиции в переписке/аналитике:** указывайте `HASH COLLECTION`
   (однозначно) и `NUM FULL SET` (человекочитаемо).
5. **Актуальность:** мастер меняется в течение работы; дата среза данных мастера
   указана в приложении А. При расчётах «на сейчас» перечитывайте файл.
6. Файлы в OneDrive могут быть заняты Excel-сессией инженера — при ошибках
   доступа не настаивайте, данные прочитаются позже.
