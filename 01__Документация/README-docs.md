## 5. КРАТКИЕ КОММЕНТАРИИ ПО ПУНКТАМ РЕЕСТРА

- **Отчёт о переговорах (п. 2.1)** — базовый аналитический документ: из него
  взята экономика и авансовые схемы всех заказов; PDF собирается конвейером
  `03__Проект\tools\make-pdf.cmd` (см. `AGENTS.md` § 6), в git коммитится
  после заморозки md-версии.
- **Решение №1 (п. 2.2)** — запустило выпуск ТКП по N1/N2; для N3 установило
  отсрочку, позднее заменённую Решением №2.
- **Решение №2 (п. 2.3)** — определило итоговый состав N3 (выведены
  `L8050 stand-alone`, `C80/master`, `C80/slave`) и требование **одновременного**
  подписания N1/N2/N3; исторические документы на прежнее лицо заказчика не
  переписываются.
- **Реестр корректировок (п. 3.1)** — единственный канал урегулирования расхождений
  подписанной версии (битые банковские реквизиты стороны заказчика, дата договора
  «01» сентября, опечатка модели в У.4 Спецификации № 1, архивные счета на прежнее
  лицо); статусы строк — 🔴 блокер / ⚠️ уточнение / ℹ️ к сведению / 🎯 действие.
- **Презентация митапа (п. 3.2)** — внутренний документ, не для внешних рассылок;
  содержит сводные показатели портфеля.
- **Акты (п. 4)** — каталоги заведены по стандарту ИРП; пустой каталог на этапе
  старта — норма, а не упущение.
- **Переписка (п. 4)** — в рамке фактически идёт обмен документами через ЭДО;
  подписанные выпуски хранятся в `04__Договор\`, а не в `Переписка\`.

## 6. ПОРЯДОК ВЕДЕНИЯ

1. Новый документ раздела регистрируется строкой реестра **в день появления**
   (дата, источник, содержание, статус).
2. Реестровые данные писем (номера, темы, статусы отправки) хранятся **только**
   в `README-mail-*.md`; в этот реестр и в корневой `README.md` выносится
   лишь путь к реестру.
3. Изменение статуса строки — с датой; исторические значения не затираются.
4. Файлы-артефакты указываются копированием пути (в backticks); гиперссылки
   ставятся только на реестры `README-*.md`.
5. При каждом изменении раздела агент предлагает соответствующую строку/статус
   в этот реестр (см. `AGENTS.md` § 1.2).
