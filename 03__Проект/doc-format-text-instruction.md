# ФОРМАТ И РЕГЛАМЕНТ ПРОЕКТНОГО ДОКУМЕНТИРОВАНИЯ — переходный контекст
## Среда: экосистема HorizonBI · ГК «ПЕРЕДОВЫЕ РЕШЕНИЯ» · рамочный проект 8/2026-N0-ГОРИЗОНТ

> **Назначение.** Полная, самодостаточная инструкция по формированию, оформлению и
> отслеживанию проектной документации для AI-агента, работающего в среде HorizonBI
> (Excel-книги спецификаций, модули Power Query (M), JSON-конфигурации DSL, `IDconfig`).
> Инструкция фиксирует практики, наработанные в проектном репозитории
> `1_2026-N2-МАС` (экосистема HorizonBI) и обязательные к воспроизведению во всех
> проектах холдинга.
>
> **Что вне зон действия.** Правила коммуникации агента с пользователем, ритуалы
> планирования/исполнения — адресат проинструктирован отдельно. Здесь регламентируется
> только **документация**: структура, имена, формат, версионирование, связи, контроль.

## 1. ФИЛОСОФИЯ ДОКУМЕНТАЛЬНОЙ СИСТЕМЫ

1. **Документация — многослойная система, а не набор файлов.** Каждый слой имеет
   свою аудиторию и свою ответственность. Нарушение границ слоёв (детали реализации в
   манифесте, системный контекст в специализированном README) считается дефектом.
2. **Единый источник истины.** Для развивающихся объектов (составы команд DSL,
   перечни функций библиотек, структуры таблиц) источник истины — **исходный код и
   фактические файлы**, а не текст документации. Документация ссылается на источник,
   но не дублирует его перечень.
3. **Утверждения проверяются фактом.** Любое утверждение документа о файле/таблице/
   поле должно воспроизводиться сканированием самого файла. Память и прошлые срезы
   нормативной силы не имеют; допустимы только с пометкой даты и примечанием
   «истине подлежит перечитанный файл».
4. **История не переписывается.** Журналы, завершённые записи статусов, принятые
   решения дописываются, а не редактируются задним числом. Устаревание исправляется
   новой записью со ссылкой на старую.

### 1.1. Пять слоёв документации (иерархия чтения AI-агентом)

| Слой | Файл | Аудитория | Ответственность |
|:-:|---|---|---|
| 1 | `AGENTS.md` (корень) | любой AI-агент | бутстрап: язык, обращение, роль, обязательное first-action — чтение слоя 2 |
| 2 | `GEMINI.md` (корень) | AI-агент проекта | системный манифест: роли/правила, бизнес-контекст, ИРП, навигация, статусы/дорожная карта |
| 3 | `README.md` (корень) | пользователь, новые участники | центральный хаб: обзор экосистемы, навигация, версия документации |
| 4 | `README-{компонент}.md` | инженер/разработчик компонента | детальная техническая документация, живёт в директории компонента |
| 5 | `ai-{шифр}.md`, `doc-*.md` | агент/внешние агенты | журнал работ (append-only) и переходные документы |

Временные агрегаты (`temp/`, `doc-temp/`) — нулевой слой: не источник истины,
подлежат регенерации, изолируются в `.gitignore` (кроме осознанно отслеживаемых).

## 2. СТРУКТУРА ПРОЕКТА (ИРП) И РАЗМЕЩЕНИЕ ДОКУМЕНТОВ

### 2.1. Правило корневого каталога проекта

```
{НОМЕР-ДОГОВОРА}_{ГГОД}-N{НОМЕР-ЗАКАЗА}-{КОМПАНИЯ}
примеры: 8_2026-N1-Горизонт ; 1_2026-N2-МАС
```

* Официальный шифр содержит слэш: `8/2026-N1-ГОРИЗОНТ`. В файловых именах слэш
  **всегда** заменяется на `_` (запрещён в именах Windows/OneDrive/Linux).
* Внутри данных (поле `NUM PROJECT`) используется официальный шифр со слэшем и
  ЗАГЛАВНЫМ названием юрлица; в путях — файловый вариант. Оба написания легитимны
  и не должны «унифицироваться».

### 2.2. Нумерация каталогов

* Все каталоги верхнего уровня и внутри `03__Проект` — префикс `NN__`
  (`01__`, `02__`, …), разделитель — **два underscores**.
* Каталоги спецификаций пронумерованы по типу: `20__work_spec`,
  `30__to_customer_tech`, `40__to_customer_fin`, `50__from_customer`,
  `60__to_supplier`, `70__from_supplier`, `80__purchase`, `90__shipment`.
* Специализированный README компонента размещается **в каталоге компонента**,
  а не в свалке корня. Исключение — три корневых файла слоёв 1–3.

### 2.3. Правило актуальных ревизий

В репозитории хранится **только новейшая ревизия** кодового файла (например,
`…rev.05 v03.m`). Старые ревизии удаляются из рабочего дерева — история живёт в git.
Устаревшие копии в каталогах данных помечаются в документации как устаревшие
(см. 8_2026-N2: `03__ТКП\02__Участники\` содержит копию `work spec rev.01`).

## 3. ИМЕНОВАНИЕ ФАЙЛОВ

| Объект | Формат имени | Пример |
|---|---|---|
| Код ETL-процессора | `ProcessingETL - {наименование} rev.NN vNN.m` | `ProcessingETL - процессор rev.05 v03.m` |
| Библиотеки M-функций | `{Имя} rev.NN vNN.m` | `UtilsFunctionVector rev.08 v07.m` |
| DSL-конфигурации | `ProcessingDSL - {тип-спецификации} - typeN.json` | `ProcessingDSL - to customer fin - type1.json` |
| Ключ `IDconfig` книги | = базовое имя файла DSL без расширения | `ProcessingDSL - to customer fin - type1` |
| Шаблон мастер-спецификации | `NN__ШАБЛОН-спецификация {тип} rev.NN vNN #{год}.xlsx` | `20__ШАБЛОН-спецификация work spec rev.05 v03 #2026.xlsx` |
| Выходная производная спецификация | `NN__Спецификация-{заказчик} - заказ {N} - {тип} #{шифр-нижним-регистром}.xlsx` | `40__Спецификация-Точные машины - заказ 1 - to customer fin #8_2026-n1-горизонт.xlsx` |
| Исходный заказ заказчика | `Заказ-№ {N} - {заказчик} - {предмет} #{шифр}.docx` | — |
| Специализированный README | `README-{компонент}.md` | `README-etl-processor.md` |
| Журнал проекта | `ai-{шифр-нижним-регистром}.md` | `ai-8_2026-n0-горизонт.md` |
| Переходные документы | `doc-{тема}.md` | `doc-работа-с-проектными-спецификациями.md` |

**Версионирование `rev.NN vNN`:** `rev` — архитектурная ревизия (состав/семантика),
`v` — исправления внутри ревизии. Версия обязана присутствовать **и в имени файла,
и в заголовке-комментарии файла**. Для `.m`-модулей шапка — блок комментариев
`// ===` с названием, версией, описанием аргументов и возвращаемого значения.

## 4. СТАНДАРТЫ MARKDOWN-ОФОРМЛЕНИЯ

### 4.1. Общие

* Язык документации — русский. Техническая лексика (имена таблиц, колонок, команд)
  — в оригинальном регистре, в backticks: `TabSpecificationWork_1`.
* Заголовки разделов — `## N. ЗАГОЛОВОК` (нумерация обязательна, CAPS).
  Подразделы — `### N.M.`.
* Крупные документы (>150 строк) обязаны иметь секцию `## ОГЛАВЛЕНИЕ` со
  ссылками-якорями на разделы (`[Введение](#1-введение)`).
* Разделители секций — `---`.

### 4.2. Таблицы

* Обязательны выравнивающие маркеры (`| :--- | :---: |`).
* Статусные и смысловые эмодзи — только из утверждённого набора (§ 4.4).

### 4.3. Блоки кода и схемы

* Код-блоки всегда с language-tag: ` ```json `, ` ```m `, ` ```excel `, ` ```text `.
* Архитектурные схемы — mermaid `flowchart TD|LR` с фиксированной палитрой classDef:

```
classDef storage fill:#E3F2FD,stroke:#1565C0,stroke-width:2px,color:#0D47A1;
classDef engine  fill:#FFF3E0,stroke:#E65100,stroke-width:2px,color:#BF360C;
classDef lib     fill:#E8F5E9,stroke:#2E7D32,stroke-width:2px,color:#1B5E20;
classDef output  fill:#F3E5F5,stroke:#7B1FA2,stroke-width:2px,color:#4A148C;
```

### 4.4. Набор статусных маркеров (закрытый)

| Маркер | Значение |
|:-:|---|
| ✅ | выполнено / подтверждено фактом |
| 🔄 | в работе |
| ⚪ | без изменений (в отчётах актуализации) |
| 🟡 | перезагрузить данные/конфигурацию (не код) |
| 🔴 | заменить (код изменился, действия обязательны) |
| ❌ | запрещено / не выполняется / сломано |
| ⚠️ | важное предупреждение (callout `> ⚠️ **Важно:** …`) |
| ❓ | открытый вопрос |
| 🎯 | план (в дорожной карте) |
| 📄 📘 💰 🔧 | иконки навигационных списков |

* Callout-важности: `> ⚠️ **Важно:** текст` — единственный формат предупреждений.
* Цитаты-назначения документа: блок `>` сразу под заголовком.

### 4.5. Подвал версии

Корневой `README.md` завершается блоком:

```
**Версия документации:** X.Y (Синхронизировано с ядром `rev.NN vNN` и шаблоном `rev.NN vNN #{год}`)
**Дата актуализации:** DDMonth YYYY г.
```

X.Y растёт на 0.1 при содержательных правках. Подвал — индикатор актуальности всей
документационной системы проекта.

## 6. ПРОЦЕССЫ: СИНХРОНИЗАЦИЯ, КОММИТЫ, ОТЧЁТЫ

### 6.1. Правило синхронизации «код → документация»

Ни один коммит, изменяющий модули (`.m`, DSL `.json`, шаблоны `.xlsx`), не
считается завершённым без синхронизации документации: версия ядра в «Паспорте
компонента», подвал версии корневого README, затронутые разделы специализированных
README, статусы §5 манифеста.

### 6.2. Формат сообщения коммита

* Префикс conventional: `feat:` / `fix:` / `docs:` / `refactor:` (+ опционально
  область `feat(dsl):`).
* Заголовок — предметное предложение на русском, что и зачем.
* Тело — нумерованные разделы по блокам изменений (код/конфигурации/документация/
  верификация), включая результаты проверок («JSON 4/4 валидны», «diff = 3 строки»).
* Никаких секретов и внешних ссылок-токенов.

### 6.3. Обязательный финальный отчёт агента (регламент манифеста)

Коммит/изменение, затрагивающий PQ-модули, сопровождается таблицей актуализации
**в финальном отчёте, без напоминания со стороны пользователя**:

| PQ-запрос в Excel | Файл-источник в проекте | Статус |
| :--- | :--- | :---: |
| `ProcessingTable` | `ProcessingETL - процессор rev.05 v03.m` | 🔴/⚪ |
| `TabConfigJSON` (записи) | `ProcessingDSL - *.json` | 🟡 |

* 🔴 **ЗАМЕНИТЬ** — код модуля изменился: заменить запрос во всех книгах.
* ⚪ — код не менялся: книги трогать не нужно.
* 🟡 — изменены данные (`CONFIG_JSON`, шаблоны): перезалить содержимое.

### 6.4. Журнал проекта `ai-{шифр}.md`

* Append-only; записи хронологически вниз; заголовок записи с датой/темой.
* Внутренняя структура записи — тематические блоки `#### _Аналитика:_` и
  `#### _Решение:_`; допустимы `<br>`.
* В журнале **не исправляются** опечатки и устаревшие названия файлов прошлых записей.

### 6.5. Временные артефакты

* Рабочие срезы, агрегаты («ALL_README»), выгрузки — только в
  `03__Проект\temp\` или `03__Проект\doc-temp\`.
* Агрегаты никогда не патчатся вручную — только пересборка из источников; иначе
  они демотивируют (содержат устаревшие срезы правил).
* Такие директории, как правило, изолируются `.gitignore` (кроме осознанных
  исключений по решению пользователя).

### 6.6. Контроль перед сдачей изменения (чек-лист)

- [ ] новые/изменённые тексты — валидность форматов (JSON парсится, markdown
      читается, ссылки относительны);
- [ ] grep-проверка: остаточные старые имена/пути/регистр/дубли правил;
- [ ] сверка фактических объектов (сканирование файла), а не памяти;
- [ ] подвал версии README обновлён (X.Y, дата, синхронизация версий);
- [ ] статусные разделы §5 манифеста актуализированы;
- [ ] финальный отчёт с таблицей актуализации модулей (§ 6.3) сформирован.

## 7. ПРАВИЛА ПО ТИПАМ ДОКУМЕНТОВ

### 7.1. `AGENTS.md` (слой 1)

Максимально краток (единицы строк): язык общения, форма обращения, роль агента,
**обязательная цепочка инициализации** (первое действие любой сессии — чтение
системного манифеста по абсолютному `file:///`-пути). Никакого содержательного
материала.

### 7.2. Системный манифест `GEMINI.md` (слой 2)

Типовая структура разделов:
1. Роли и правила взаимодействия (стандарты кода, обращения);
2. Бизнес-контекст (юрлица/налоговым режимам, нумерация проектов, ИРП);
3. Система спецификаций — только обзор + ссылки на слои 3–4;
4. Архитектура — без фиксации развиваемых составов, указатель «актуальный состав — по
   исходному коду и README-справочнику»;
5. Текущий статус: §5.1 «Завершённые задачи» (хронология, нумерованный список,
   ✅-статусы), §5.2 «Текущая реализация», §5.3 «Следующие задачи» (приоритеты).
Регламент финального отчёта (§ 6.3) хранится именно здесь, в разделе 1.

### 7.3. Корневой `README.md` (слой 3)

Назначение — хаб и «первый экран человека». Обязательны: введение (что за проект,
место в холдинге), обзор с mermaid-схемой (§ 4.3), ИРП с деревом каталогов,
система спецификаций (краткая таблица типов `20…90`), ETL-обзор, навигация
(«СТРУКТУРА ДОКУМЕНТАЦИИ ПРОЕКТА»: для пользователей / для разработчиков / рабочие
документы — с эмодзи-иконками), статусы/дорожная карта, технологический стек,
контакты/реквизиты, подвал версии (§ 4.5).

### 7.4. Специализированные `README-{компонент}.md` (слой 4)

Единый скелет (см. Приложение D): «ДОКУМЕНТАЦИЯ: …» → назначение → оглавление →
нумерованные разделы → паспорт компонента (таблица «Параметр | Значение»:
идентификатор, текущая версия, среда, контракты входов/выходов, зависимости) →
реестры/таблицы данных → примеры JSON/M → troubleshooting (таблица
«текст ошибки | причина | регламент устранения») → каталог связей.
Содержательные правила: имена функций/полей/колонок — в backticks оригинального
регистра; версии команд помечать (*добавлено в rev.NN vNN*); предупреждения —
callout § 4.4.

### 7.5. Переходные документы `doc-*.md` (слой 5)

Пишутся **для конкретного адресата-агента** и промтятся как самостоятельный вход:
шапка-блокнот «Назначение» (кто адресат, что он делает, чего не делает); далее —
карты путей, таблицы объектов, семантика полей, правила поведения адресата;
приложения со справочными снимками (обязательна дата среза + дисклеймер
«истине подлежит перечитанный файл»). Ссылки на чужие хранилища допустимы
абсолютными путями (агент адресата читает файловую систему, а не git).
Примеры: `doc-работа-с-проектными-спецификациями.md`,
`doc-format-text-instruction.md` (настоящий документ).

## ПРИЛОЖЕНИЕ A. Скелет `AGENTS.md`

```markdown
# AI AGENTS MANIFEST & SYSTEM INSTRUCTIONS

## 1. БАЗОВЫЕ ДИРЕКТИВЫ СЕССИИ (Zero-Step Rules)
* **Язык общения:** Строго русский язык.
```
